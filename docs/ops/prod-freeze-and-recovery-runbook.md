## Window procedure

1. **Preconditions.** Record approval, candidate SHA and complete manifest SHA-256. Verify the package with `Test-ReleaseCandidate -RequireMigrationIntegrity`; require all paths and hashes to match the retained manifest. Confirm the exact protected decisions in the readiness report: the three Thiago sessions, the approved class-C digest, and the two-tenant activation allowlist. No PRD action is permitted by this runbook alone.
2. **Block new work and relaunch.** Put the user-facing maintenance notice in place. Save current enabled states for `QuiverTap-AtStartup`, `QuiverTap-AtLogon`, and `QuiverTap-ProdBackup`, then disable them. Create `deploy/runtime/deploy.pause`. Stop Cloudflared ingress, the alert poller, Ops panel, watchdog and API. Do not use a force-kill before draining. Keep uploads and all user writes unavailable during the window.
3. **Drain and attest.** After ingress is closed, wait for in-progress API operations to finish. On the old runtime, inspect production `pg_stat_activity` for active queries and open transactions belonging to application writers; require none for two consecutive checks 30 seconds apart. If any query/transaction remains after five minutes, abort without migration. Then stop the API and confirm no API listener, matching application process, active write transaction, upload handler or relaunch task is running. Start the retained candidate only with `QUIVER_WRITE_FREEZE_FILE` pointing to the existing marker; owner `GET /api/operacao/write-freeze-status` must report `blocked=true` and `inFlightWrites=0`. During the freeze, only this revision's owner-authenticated administrative closure endpoint can write; all other HTTP writes must return 503 `WRITE_FREEZE_ACTIVE`.
4. **Create one synchronized checkpoint.** While all writers are stopped and the marker is present, save the PostgreSQL dump, complete `backend/uploads-prod` tree, protected production configuration (encrypted/access-controlled; no secret values in the receipt), active runtime and rollback runtime. Record one checkpoint ID and UTC start/end. Inventory every file with relative path, size, mtime UTC and SHA-256; hash the dump, configuration and runtime manifests. Repeat the writer/transaction check after collection. If any write appears or any file changes, discard the checkpoint pair and start again. Do not release the freeze between these captures.
5. **Run the rehearsed transition.** Stage the exact retained package; do not rebuild from the mutable checkout. Apply only the migrations and bounded data changes in the approved sequence, under the exact snapshot/digest guards. Keep ingress, scheduled relaunchers and the freeze marker active. Perform the three administrative closures with the authenticated owner and approved reason; this records current UTC/operator/audit, preserves unknown counts, payments, and links, and leaves financial reconciliation pending. Apply only the existing two-company activation allowlist; all other tenants remain LEGACY. Apply the approved class-C disposition only when the live source-set digest matches the approved digest exactly.
6. **Validate under freeze.** Verify migration ledger/checksums, session status and null counts, audit identity/time/reason, zero payment/movement effects from administrative closures, class-C IDs/values/links and digest, activation allowlist, tenant isolation, readiness, and uploads hashes. Smoke only the approved login, session-list/report, and one controlled operational read/write path needed to prove service readiness. The normal-write refusal must remain active; only the owner administrative endpoint is an allowed maintenance write. Record screenshots/console/network/persistence evidence for UI checks. Keep the freeze until every criterion passes.
7. **Abort and restore.** Abort on candidate/manifest mismatch, checkpoint/hash drift, unexpected writer, failed migration/checksum, scope/digest mismatch, cross-tenant effect, unknown count/payment/link change, audit gap, failed readiness/smoke, or forecast window exhaustion. Keep ingress and tasks disabled. Restore the database dump, uploads tree, protected configuration, and previous runtime as one compatible set; re-hash all restored materials, verify readiness and rollback smoke, and only then remove the write-freeze marker. Restore the saved service/task states and reopen ingress after acceptance. If full restore is not verified, keep the service closed and escalate; never release writes onto a mixed database/runtime/files state.
8. **Release writes.** With the exact candidate and reconciliations accepted, remove the freeze marker, confirm the owner status reports `blocked=false`, verify one normal write succeeds and persists, then re-enable the saved tasks/service and ingress in controlled order. Capture final state and timestamps.

## Concrete execution gap

The existing `scripts/prod/deploy.ps1` builds from the mutable checkout and its integrated database work runs Prisma migrations plus `ClienteEstatisticas` backfill. `Publish-ReleaseCandidateArtifacts` validates/copies an immutable candidate, but no integrated production command currently combines that copy with the PDV business transformation/replay and the exact class-C/session/activation controls above. The existing `run-pdv-unico-dev-cutover.mjs` deliberately refuses production. Do not approve or begin a production migration until that execution path is implemented and rehearsed against a fresh QA restore. This is a concrete blocker, not authorization to improvise SQL or use the DEV-only command against PRD.

## Time budget

Reserve a **75-minute window**: checkpoint and hashes 15 minutes; migration and bounded transformation 20 minutes (the representative sequence measured 18m13s and is only one component); reconciliation and targeted smoke 10 minutes; controlled stop/start and reopening 10 minutes; recovery contingency 20 minutes. The 18m13s sequence is not the total window. Checkpoint duration and full file-copy duration were not measured under this stop-the-writers procedure; if the measured checkpoint exceeds 15 minutes or migration exceeds 20 minutes, abort before the remaining time becomes inadequate. The previous complete QA restore/runtime/upload verification measured 17.493 seconds, but that is not a substitute for the 20-minute recovery reserve on the production dataset.
