Quiver Tap — Arquitetura de Observabilidade

Documento gerado em 11/08/2026 · Ambientes dev (:3002 / :5202) e prod (:3001) · Stack Elastic local

1. Visão geral

A observabilidade do Quiver Tap combina OpenTelemetry (EDOT Node), um OTel Collector, Elasticsearch e Kibana. A aplicação emite logs, traces e métricas; audit e transações de negócio vão para índices separados por empresa (slug). Alertas do Kibana (licença Basic) são entregues por e-mail via connector .index + poller na API + SMTP.

Camadas
  • Aplicação — API Fastify + hooks de audit + registrarTransacao()
  • Emissão — Pino instrumentado + EDOT Node SDK → OTLP
  • Coleta — OTel Collector (OTLP + httpcheck + tcpcheck + hostmetrics)
  • Armazenamento — Elasticsearch (índices dinâmicos OTel)
  • Visualização — Kibana (data views, dashboards, regras)
  • Alertas — ES quiver-tap-alert-events → worker dedicado → e-mail

3. Fluxo de telemetria da aplicação

  1. Requisição HTTP entra no Fastify; hooks resolvem contexto (slug, actor, env).
  2. Mutações e erros geram emitAuditEvent (HTTP audit).
  3. Operações de negócio chamam registrarTransacao() → grava TransacaoLog no Postgres e emite audit com transacao.payload.
  4. Prisma extension audita SQL (db.*), com amostragem configurável em leituras.
  5. Tudo passa pelo logger Pino singleton (instrumentado) → EDOT exporta logs, traces e métricas via OTLP.
  6. Collector aplica namespace dev ou prd e indexa no Elasticsearch.

6. Alertas por e-mail (Kibana Basic)

Licença Basic não permite connectors nativos .email / .webhook. Fluxo alternativo:

Kibana Rule (ex.: API down, 5xx, event loop) │ ▼ Connector .index ──► ES: quiver-tap-alert-events │ ▼ startKibanaAlertPoller() no worker (intervalo ~30s) │ ▼ handleKibanaAlertWebhook() ──► SMTP (Hostinger) ──► OBS_ALERT_EMAIL_TO

Worker de alertas

O poller roda em backend/src/alert-poller-worker.ts (health :3098/health), gerenciado por npm run alert-poller:start e scripts/prod/ensure-running.ps1. Estado persistente em deploy/runtime/alert-poller-state.json. A API só faz poll se KIBANA_ALERT_POLL_IN_API=true.

Outside-in e SLO

  • URLs públicas no collector + Kibana Uptime + UptimeRobot (ver outside-in.md)
  • SLI/SLO documentados em sli-slo.yml; dashboards SLO e Business no Kibana
  • Relatório mensal: npm run obs:report-slo

8. Limites conhecidos (não é 100% de tudo)

  • Traces: tail sampling — erros, lentos (>500ms) e ~15% probabilístico; maioria das requisições normais não traceada.
  • Audit HTTP: GET 2xx e rotas de polling/health/assets ignorados.
  • Transações com payload: fluxos principais (quiosque, comandas, eventos, portal, caixa, estoque); nem toda rota CRUD.
  • Infra: collector cobre origin, URLs públicas e TCP Postgres; probe externo (UptimeRobot) documentado.
  • Alertas: latência de até ~30s (poller worker); depende de regras Kibana ativas e SMTP configurado.
  • Deploy: fixes recentes de export audit OTel validados em dev; prod reflete após deploy autorizado.
